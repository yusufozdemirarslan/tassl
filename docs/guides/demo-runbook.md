# Tassl demo runbook

For the presenter of a judged, non-commercial demo of Tassl on the production deployment. It has five parts: the warm-up an hour before, the demo path click by click with what to say, the break-glass table, the fully offline fallback, and the seat plan. Every line is a statement of what you do, in the order you do it.

## The facts this runbook rests on

- Production is https://tassl.vercel.app. It runs on Vercel Hobby (Fluid compute, 300 s maximum function duration, region iad1) and Neon Free (the database compute suspends after 5 idle minutes; the measured cold start on `/api/ready` is 2.2 s, the warm response 0.16 s).
- The production workflow (GitHub Actions `production.yml`) takes 41 minutes end to end: checks 37.5 min, deploy 3.3 min. Nothing merges to `main` after the T-60 warm-up starts.
- The demo runs on the seeded scenario package **Meridian Roast (fixture)**, version 1, and its three seeded assignments on section A of the course **Marketing Strategy Walkthrough**: **Decision Run 1 (walkthrough)** (defective variant), **Decision Run 1 (sound)** (sound variant), **Auto-lock test run** (defective variant, 120-second working clock). All three are walkthrough assignments (`src/server/db/seed.ts`), so a run on any of them is deleted from its assignment page and the demo can be repeated on the same seat. The same seed exists locally and in production.
- The seat accounts and where their password is: `docs/guides/README.md` and `docs/qa/demo-accounts.md`. Email + password is the demo login. Google sign-in is secondary and admits only the accounts listed as test users on the Google Cloud consent screen (the app is in Testing status).
- The clocks are real. The Turn arrives 90 seconds after the decision is filed; the auto-lock run ends two minutes after its frame is locked; the working clock is 25 minutes; scoring takes under 5 seconds on the scripted assistant and a few seconds more on the live model. The test-only advance-clock route does not exist in production.
- The assistant in production is the live model. Its prose differs from run to run; the claim cards do not, because the scenario's authored trigger phrases decide which claims surface. A live reply takes 3 to 13 seconds.

## 1. T-60 minutes: warm-up

1. Open the Neon dashboard (console.neon.tech, the Tassl project, Usage) and write down three numbers: compute hours used this month against the 100 CU-hour allowance, storage against 0.5 GB, and the branch count, which is under 10.
2. Open the Vercel usage page (vercel.com, the Tassl team, Usage) and confirm no allowance shows a warning; Fluid compute active CPU and function invocations are inside the Hobby limits.
3. Open Sentry (the Tassl project, Issues) and confirm nothing new arrived in the last 24 hours. An issue that did arrive is read now, not during the demo.
4. From the repository root on the presenter laptop, run `PLAYWRIGHT_BASE_URL=https://tassl.vercel.app SEED_PASSWORD="$(cat ~/.config/tassl/seed-password.txt)" pnpm demo:warm`. `SEED_PASSWORD` is the production seat password (`docs/qa/demo-accounts.md`); without it the script signs in with the local default, which production refuses. It hits `/api/ready`, then loads every demo-path page as the demo instructor and the demo student, so Neon is awake and the functions are warm. It ends with `demo:warm passed` and exits 0.
5. Sign in to production once as each seat, each in its own browser profile (part 5): instructor@tassl.local, student1@tassl.local, student2@tassl.local, editor@tassl.local, admin@tassl.local. Each sign-in ends on **Home**. Sign the student profile back out and leave it on **Sign in to Tassl** with student1@tassl.local typed in **Email address**.
6. As the instructor, clear every run a rehearsal left on the three seeded assignments, all three of which are walkthrough assignments: **Courses** → **Marketing Strategy Walkthrough** → **Assignments** → **Decision Run 1 (walkthrough)** → in **Runs**, press **Delete** on each row → **Delete this walkthrough run?** → **Delete the run** → toast **The walkthrough run was deleted.** Then **Back to the course** → **Assignments** and the same on **Decision Run 1 (sound)** and on **Auto-lock test run**. No run is voided to clear a seat: voiding keeps the record and re-offers the run; deleting removes it. A run's replay, when one is wanted, is reached the same way, through the assignment's **Runs** table and **Open the replay** on the student's row (part 2 step 12), never by typing an address.
7. As the admin, open **Admin** → **Flags** and confirm: **FEATURE_AI** **On**, **FEATURE_TEST_CONTROLS** **On**, **Effective model provider** `openai-compatible`, **Assistant mode** **Live model**, and **Model usage** well inside the monthly budget sentence ("The month has used … of the … tokens").
8. Open `docs/qa/PRE-DEMO-CHECKLIST.md` and tick every row. Open this runbook's part 3 (break-glass) on the second screen and leave it there.
9. Set the projector: Windows Settings → System → Display → Display resolution **1920 × 1080**, Scale **125%**; browser zoom **100%** (Ctrl+0) in every profile. The app is tested at that size.
10. Rehearse the offline fallback (part 4) once on this laptop the day before; at T-60, confirm `bash scripts/pg-local.sh status` exits 0 and the local build from that rehearsal still exists.

Labels are the exact words on the screen, in bold; where a word appears on more than one row or card, the row or card it sits on is named in plain words. "Say" is one or two sentences to read aloud about what is on the screen at that moment.

## 3. Break-glass

Two layers of assistant kill switch exist. Layer 1 is the Platform admin's **Assistant mode** control on https://tassl.vercel.app/admin/flags (signed in as admin@tassl.local): the radios **Live model** and **Scripted assistant**, the button **Save assistant mode**; it takes effect on the next assistant request, with no redeploy. Layer 2 is the environment route, which forces the scripted assistant for the whole deployment in about 4 minutes:

```
printf mock | npx vercel@59.11.2 env add LLM_PROVIDER production --force --no-sensitive
npx vercel@59.11.2 redeploy "$(npx vercel@59.11.2 ls --prod 2>/dev/null | grep -o 'https://[^ ]*' | sed -n 1p)"
```

The deployment URL in the second line is the first URL printed by `npx vercel@59.11.2 ls --prod`. Rollback to the previous production deployment takes about one minute:

```
export PREV_URL="$(npx vercel@59.11.2 ls --prod 2>/dev/null | grep -o 'https://[^ ]*' | sed -n 2p)"
npx vercel@59.11.2 rollback "$PREV_URL"
bash scripts/smoke.sh https://tassl.vercel.app
```

The smoke script prints one `ok   /path -> 200` line per check and ends with `smoke passed for https://tassl.vercel.app`; a failed check prints `FAIL` and the script exits 1.

|---|---|---|---|

## 4. The fully offline fallback

The laptop carries a complete Tassl with the scripted assistant and a local Postgres. From the repository root, in Git Bash:

```
set -a; . ./.env.test; set +a
bash scripts/pg-local.sh start
pnpm demo:reset
pnpm build
pnpm start
```

Then open http://localhost:3000 in each browser profile and sign in with the seat accounts and the password `Walkthrough-Pass-2026`.

What each line does:

- `set -a; . ./.env.test; set +a` exports the test environment: `LLM_PROVIDER=mock`, `FEATURE_AI=false` (the scripted assistant, deterministic, no digits in its prose, no network), `FEATURE_TEST_CONTROLS=true`, `APP_ENV=test`, `SEED_PASSWORD=Walkthrough-Pass-2026`, and the local database URL.
- `bash scripts/pg-local.sh start` starts the portable Postgres 17 cluster on port 5432 and ensures the `tassl` and `tassl_test` databases exist. On a laptop that has Docker instead of the portable binaries, the equivalent line is `docker compose up -d`.
- `pnpm demo:reset` restores the seeded demo state (the seat accounts, the course, the three walkthrough assignments, the confirmed package), deletes every run on the three assignments, and then builds two runs on student2@tassl.local through the scripted assistant: **Decision Run 1 (walkthrough)** taken all the way to recorded (scored, one band overridden with a note, the remaining drafts confirmed, export version 1 written, the debrief's two questions answered) and **Auto-lock test run** left at scored, waiting in the review queue. student1@tassl.local is left with no run, so it is the free seat for the live demo, and the review, debrief, record and export screens are never empty. It waits the real 90 seconds for the Turn and takes about two and a half minutes. The same script runs against production from the operator's machine, as the header of `scripts/demo-reset.ts` documents: `DATABASE_URL=<owner string> DATABASE_URL_UNPOOLED=<owner string> SEED_PASSWORD="$(cat ~/.config/tassl/seed-password.txt)" APP_ENV=production pnpm demo:reset`.
- `pnpm build` then `pnpm start` serve the production build on port 3000.

What is different offline: the assistant's prose is scripted (the claim cards and every screen are the same); **Continue with Google** is absent from **Sign in to Tassl** because no Google client id is set; emails are written to `test-results/emails` instead of being sent; **Admin** → **Flags** shows **FEATURE_AI** **Off** and **Effective model provider** `mock`. The clocks are the same as in production: the Turn at 90 seconds, the auto-lock at two minutes, the working clock at 25 minutes. The test-only advance-clock route exists under `APP_ENV=test`; the demo does not use it.
